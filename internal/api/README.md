# internal/api: el plano de control

Implementación de `docs/api.md` para la Fase A. Un binario (`cmd/rampa-api`) que expone la API REST, el stream SSE de eventos, el hub WebSocket de agentes y sirve la SPA.

## Correr en desarrollo

```sh
export PATH="$HOME/.local/bin:$PATH"   # go 1.27
go run ./cmd/rampa-api serve --dev
```

`--dev` hace cuatro cosas:

1. Arranca un Postgres embebido ([fergusstrange/embedded-postgres](https://github.com/fergusstrange/embedded-postgres)) con datos en `~/.local/share/rampa/pg` y puerto `54329`. La primera vez descarga los binarios (~30 MB) a `~/.embedded-postgres-go`.
2. Setea `RAMPA_DEV_LOGIN=true`, así `POST /v1/auth/dev-login {"email": "..."}` abre sesión sin IdP.
3. Setea un `RAMPA_SESSION_SECRET` fijo de desarrollo para que las sesiones sobrevivan reinicios.
4. Setea una `RAMPA_STATE_KEY` fija de desarrollo, así el runner de OpenTofu queda habilitado si hay `tofu` en el PATH (ver más abajo). Nunca uses esa clave contra una cuenta real: es pública.

Cualquier variable `RAMPA_*` que ya esté en el entorno gana sobre los defaults de `--dev`. Sin `--dev`, hacen falta como mínimo `RAMPA_DATABASE_URL` y `RAMPA_SESSION_SECRET` (32+ bytes). La tabla completa está en `docs/api.md`.

Un flujo mínimo con `curl`:

```sh
API=http://localhost:8080
curl -c c.txt -X POST $API/v1/auth/dev-login -d '{"email":"vos@acme.com"}'
curl -b c.txt -X POST $API/v1/orgs -d '{"slug":"acme","name":"Acme"}'
curl -b c.txt -X POST $API/v1/orgs/acme/cloud-accounts -d '{"provider":"aws","name":"acme-nonprod","region":"us-east-1"}'
# ... PATCH con el ARN, POST .../verify, POST /clusters, POST /apps con el rampa.yaml, POST .../deployments
# DigitalOcean (auth token): el token se manda una vez y queda cifrado con RAMPA_STATE_KEY.
curl -b c.txt -X POST $API/v1/orgs/acme/cloud-accounts -d '{"provider":"digitalocean","name":"acme-do","region":"nyc3","settings":{"registry_name":"acme"}}'
curl -b c.txt -X PATCH $API/v1/orgs/acme/cloud-accounts/<id> -d '{"credentials":{"api_token":"dop_v1_..."}}'
```

Otros subcomandos: `rampa-api migrate` aplica las migraciones pendientes y termina (también acepta `--dev`). `serve` corre las migraciones al arrancar.

### Infraestructura con OpenTofu en local

Los endpoints `/infra` (crear un cluster EKS con clicks) responden `501 not_implemented` hasta que el runner esté listo. Hacen falta dos cosas además de `--dev`:

```sh
export PATH="$HOME/.local/bin:$PATH"                 # tofu 1.12 está ahí; RAMPA_TOFU_BIN=tofu lo busca en el PATH
export RAMPA_STATE_KEY="$(openssl rand -base64 32)"  # clave AES-256 del estado; --dev pone una fija si no la definís
export RAMPA_AWS_TRUSTED_PRINCIPAL_ARN=arn:aws:iam::<cuenta de Rampa>:user/rampa-dev   # identidad con la que corre la API
go run ./cmd/rampa-api serve --dev
```

`GET /v1/orgs/{org}/infra/modules` lista los módulos con `kind` (`cluster` o `vm`), `secret_store` por defecto y sus `inputs` tipados (`string`, `list`, `bool`, `number`, con `default`, `options` y `required`), y dice en `runner_ready` si el runner puede ejecutar y en `runner_error` qué falta. Disponibles: `aws/eks-cluster`, `aws/ec2-k3s`, `digitalocean/doks-cluster` y `digitalocean/droplet-k3s`. El flujo completo:

```sh
# cuenta connected (ver arriba) y después:
curl -b c.txt -X POST $API/v1/orgs/acme/infra/clusters -d '{"cloud_account_id":"...","name":"rampa-nonprod","env":"nonprod","domain":"apps.dev.acme.com","inputs":{"kubernetes_version":"1.33","admin_principal_arns":["arn:aws:iam::123456789012:user/juan"]}}'
# una VM con k3s en DigitalOcean: module explícito e inputs del módulo
curl -b c.txt -X POST $API/v1/orgs/acme/infra/clusters -d '{"cloud_account_id":"...","module":"digitalocean/droplet-k3s","name":"do-dev","env":"nonprod","domain":"apps.dev.acme.com","inputs":{"size":"s-2vcpu-4gb","admin_cidrs":["203.0.113.0/24"]}}'
curl -b c.txt $API/v1/orgs/acme/infra/runs/<id>/log?stream=1     # SSE: line, status, done
curl -b c.txt -X POST $API/v1/orgs/acme/infra/runs/<id>/destroy
```

Los campos `kubernetes_version`, `vpc_cidr` y `admin_principal_arns` al nivel raíz del body siguen aceptándose (formulario viejo de EKS) y se funden en `inputs`. `module` vacío es el módulo `cluster` del provider de la cuenta. Los inputs se validan con `infra.ValidateInputs` contra lo que declara el módulo (tipo, opciones, requeridos, defaults, chequeos extra como CIDRs y ARNs); una clave desconocida es `invalid`.

El runner escribe cada run en `RAMPA_INFRA_WORKDIR` (default el temp del sistema): `main.tf` generado, `rampa.auto.tfvars.json` con los inputs no sensibles, `modules/<provider>/<módulo>` desde `terraform/modules` y `charts/rampa-agent` desde `charts/`. Comparte un cache de providers en `<workdir>/rampa-tofu-plugin-cache` para no bajar los providers en cada apply. El directorio del run se borra al terminar. Variables: `RAMPA_TOFU_BIN`, `RAMPA_STATE_KEY`, `RAMPA_INFRA_WORKDIR`, `RAMPA_INFRA_TIMEOUT` (40m), `RAMPA_INFRA_CONCURRENCY` (2); la tabla completa está en `docs/api.md`.

El backend `http` de estado que usa `tofu` es la propia API (`/v1/tfstate/{run}`), así que `RAMPA_PUBLIC_URL` tiene que ser alcanzable desde donde corre el runner (en `--dev`, `http://localhost:8080` alcanza). Para probar sin AWS, `internal/api/infra/testdata/fake-tofu.sh` es un `tofu` de mentira que imprime líneas, guarda un estado por el backend http y devuelve outputs fijos: `RAMPA_TOFU_BIN=$PWD/internal/api/infra/testdata/fake-tofu.sh`.

## Tests

```sh
go test ./internal/api/...            # todo
go test ./internal/api/server/        # integración con Postgres embebido
RAMPA_TEST_SKIP_DB=1 go test ./internal/api/...   # sin base: salta la integración
```

- **Unitarios sin base**: `config`, `crypto` (AES-GCM y credenciales con el id de la cuenta como AAD), `auth` (cookie HMAC, tokens de API, cluster y bootstrap, roles, resolución de idioma con `Accept-Language`), `events` (fanout y `Broadcast`), `deploy` (render del chart con `examples/checkout-api/rampa.yaml`: dev tiene Deployment, prod tiene Rollout y HPA), `hub` (agente falso por WebSocket con `httptest`: welcome, comando, ack, event, result, reenvío al reconectar, watchdog de heartbeats, `Send` en vivo), `httpapi` (helpers, `install_command`, limitador de intentos) y en `infra` el registro de módulos con sus inputs exactos, `ValidateInputs`, el root module generado por provider (si hay `tofu` en el PATH, `tofu init -backend=false` y `validate` lo comprueban contra los módulos embebidos) y la escritura del workdir. `server/chart_test.go` empaqueta el chart del agente y lo carga con `loader.LoadArchive` del SDK de Helm.
- **Con base** (`infra`, vía `store/storetest`): el backend http de estado (401 sin token o con token de otro run, 404 sin estado, POST/GET ida y vuelta, Basic y Bearer, LOCK/UNLOCK, 423 con otro ID, 409 en POST con ID incorrecto, la fila cifrada no contiene el texto plano) y el runner con el `tofu` falso de `testdata`: estados en orden, log por líneas y en vivo, outputs sin los sensibles, cluster con `agent_role_arn`, token del cluster rotado y bootstrap token emitido (nunca en el log ni en los inputs), credenciales ausentes del log y de los eventos, destroy que borra el cluster, fallo con pista de permisos, retry, recuperación de runs huérfanos, un run por cuenta de nube, y un módulo `vm` de DigitalOcean con el provider real como `CredentialsProvider`: el token sale del cifrado y llega al subproceso como `DIGITALOCEAN_TOKEN` sin variables de AWS. Corren con `-race`.
- **Integración** (`server`): levanta un Postgres embebido en un puerto libre y un directorio temporal, una sola vez por proceso, con una base nueva por test. Corre las migraciones y ejercita el flujo completo por HTTP: dev-login, org, cuenta de nube con un provider falso registrado con `provider.Register`, verify, cluster, importar la app de ejemplo, atar el scope, pedir el deployment (queda `queued` y hay un `agent_command`), un agente falso lo lleva a `healthy`, aprobación de prod, cancelación, tokens y roles. Además, `TestTenantIsolation` prueba que un usuario de la org A recibe 404 en todo lo de la org B, y `TestEventStream` verifica el SSE. `features_test.go` cubre el spec (preview con `valid: false`, from-spec, GET y PUT spec), el `scaffold.zip` (lista de archivos, `rampa.yaml` igual al manifest, org de GitHub por query, settings o `CHANGEME`), el onboarding en cada estado y el flujo de infraestructura por HTTP con el `tofu` falso (validaciones incluidas las de `module` e `inputs`, 202, SSE del log, outputs, `install_command` con IRSA, retry, destroy, 501 sin clave o sin `tofu`). `wave_test.go` cubre la ola del ADR 0004: cuenta de DigitalOcean con el token cifrado (501 sin `RAMPA_STATE_KEY`, PATCH cifra y nunca lo devuelve, `has_credentials`, la fila no lo tiene en claro, verify contra una API de DigitalOcean simulada con `httptest` inyectada por `digitalocean.Config.BaseURL`, rotación, DELETE), bootstrap tokens (emisión, canje que rota el token y corta al agente viejo, un solo uso, vencido, 429 por IP, `install-command` sin rotar), secretos de aplicación con el agente falso (el comando llega con los valores, la fila y los eventos no los tienen, GET devuelve las claves, offline es 409, prod exige admin, target según `secret_store`), `compute` en scopes y 501 para serverless, `locale` en `/me` y la descarga del chart. Si los binarios de Postgres no se pueden descargar o `RAMPA_TEST_SKIP_DB=1`, se salta con un mensaje claro.

## Layout

| Paquete | Qué hace |
|---|---|
| `config` | Carga y valida las variables `RAMPA_*` con defaults. `Load(getenv)` para testear sin tocar el entorno. |
| `crypto` | AES-256-GCM con la clave del servidor (`RAMPA_STATE_KEY`): `Cipher.Seal/Open` con un dato autenticado por fila, y `SealCredentials/OpenCredentials` para las credenciales de las cuentas con auth token (AAD el id de la cuenta). Lo comparten `infra` (estado de OpenTofu) y `httpapi` (cuentas). |
| `store` | Pool de pgx, migraciones SQL embebidas (`migrations/0001_init.sql`, `0002_infra.sql`, `0003_runtimes_multicloud.sql`) con runner propio (`schema_migrations` y advisory lock), modelos y repositorios por entidad. Todos los métodos reciben `org_id` salvo `users`, la búsqueda de tokens por hash (API, cluster y bootstrap), la de runs por hash del token de estado y las operaciones sobre `infra_states` (que van por `run_id`, ya autenticado). `WithTx` ata un `*Store` a una transacción. Incluye `cloud_accounts.credentials_ciphertext`, `clusters.kind`, `cluster_bootstrap_tokens`, `scope_secret_keys` y `users.locale`. `store/storetest` levanta el Postgres embebido para los tests de otros paquetes. |
| `auth` | Cookie `rampa_session` firmada con HMAC-SHA256, tokens `rampa_<hex>`, `rampa_cluster_<hex>` y `rampa_bootstrap_<hex>` guardados como SHA-256, OIDC opcional con go-oidc (discovery perezoso), middlewares `RequireAuth`, `RequireOrg` (membresía o token de la org) y `RequireRole`, y el idioma de la request (`LocaleFromHeader`, `Locale(ctx)`: preferencia del usuario, después `Accept-Language`, después `es`). |
| `events` | Persistencia (vía `store`) y fanout en memoria para SSE, con filtros por `subject_type` y `subject_id`. |
| `deploy` | Pipeline de render: `render.Build` con los datos del cluster, chart `charts.RampaApp` cargado con el loader de Helm desde el `embed.FS`, `chartutil.ToRenderValues` + `engine.Render`, split de documentos, YAML a JSON, y armado del `protocol.DeployCommand` con labels y timeout. |
| `hub` | Hub de agentes por WebSocket (`coder/websocket`). Protocolo exacto de `pkg/protocol`. `Backend` es la interfaz de persistencia; `StoreBackend` la implementa con `store` y `events`. `Send` entrega un comando solo por la conexión viva (`write_secret`). |
| `infra` | Infraestructura con clicks: registro de módulos con inputs tipados (`aws/eks-cluster`, `aws/ec2-k3s`, `digitalocean/doks-cluster` y `digitalocean/droplet-k3s` disponibles; gcp, azure, oci y ovh listados como no disponibles), `ValidateInputs`, generador del root module por provider, escritura del workdir (módulos de `terraform/` y chart de `charts/` embebidos), worker que toma runs de la cola (uno por cuenta de nube, `RAMPA_INFRA_CONCURRENCY` a la vez), runner que obtiene credenciales de la cuenta (federadas o descifradas), genera el bootstrap token y ejecuta `tofu init/plan/apply` o `destroy` con log en vivo, y el backend http de estado cifrado (`/v1/tfstate/{run}`). |
| `httpapi` | Router chi con todas las rutas de `docs/api.md`, handlers, helpers JSON y errores `{"error":{"code","message","details"}}`. Incluye el spec estructurado (`/apps/preview`, `/apps/from-spec`, `/apps/{app}/spec`), el `scaffold.zip` (con los golden paths de `cmd/rampa/templates`, compartidos con el CLI), el onboarding, los endpoints `/infra`, las credenciales cifradas de las cuentas, los bootstrap tokens (`/clusters/{id}/bootstrap-token`, `/clusters/{id}/install-command`, `POST /v1/agent/bootstrap` con límite de intentos), los secretos de aplicación (`/apps/{app}/scopes/{scope}/secrets`) y `PATCH /me`. |
| `server` | Cablea todo: abre la base, migra, marca clusters offline, arma bus, hub, pipeline, runner y API; sirve la SPA desde `RAMPA_WEB_DIR` con fallback a `index.html`, `GET /public/cloudformation/rampa-connect.yaml` desde `pkg/provider/aws`, `GET /public/charts/rampa-agent.tgz` (el chart embebido empaquetado con `archive/tar` y `compress/gzip`, cacheable 5 minutos), `/healthz`, `/readyz`, `/version`. |

## Decisiones

- **El render se hace antes de persistir.** `POST .../deployments` arma values, renderiza el chart y solo entonces crea el deployment. Si el chart falla, la respuesta es `invalid` y no queda basura. Los `values` se guardan en la fila (jsonb) y el approve re-renderiza desde ahí, así lo aprobado es exactamente lo que se pidió aunque el manifest haya cambiado en el medio.
- **El comando se persiste en `agent_commands` dentro de la misma transacción que el deployment** y después se avisa al hub (`Notify`). Si el agente no está conectado, el comando espera en la cola y se manda al reconectar (queued, y sent sin ack). El `id` del `agent_command` es el `id` del `protocol.Command`.
- **Estados del deployment.** `awaiting_approval | queued | applying | progressing | healthy | failed | cancelled`. `applying`, `progressing`, `healthy` y `failed` los pone el agente vía `event` y `result`; `timeout` y `rejected` se mapean a `failed` con mensaje. Un `result` repetido tras una reconexión se ignora. Un deployment cancelado no vuelve a cambiar aunque el agente reporte.
- **Estados del scope.** `unbound` (declarado sin fila o sin cluster), `idle`, `deploying`, `healthy`, `failed`, `deleting`. Tras un undeploy exitoso los efímeros se borran y los permanentes vuelven a `idle`.
- **Un agente solo afecta su cluster.** Cada update de `agent_commands` filtra por `org_id` y `cluster_id` de la conexión; un `ack`/`event`/`result` sobre un comando ajeno no encuentra fila y se descarta.
- **Online/offline.** `online` al `hello`; `offline` al cerrar la conexión o tras 3 heartbeats sin noticias (watchdog). Al arrancar la API todos los clusters se marcan `offline` porque ninguna conexión sobrevive al reinicio. Una segunda conexión del mismo cluster desplaza a la anterior.
- **404 para quien no es miembro.** Una org donde el principal no tiene membresía (o un token de otra org) devuelve `not_found`, no `forbidden`: la org no existe para él. Los roles insuficientes dentro de la org sí dan `forbidden`.
- **Roles.** Owner > admin > developer > viewer. Prod (desplegar, aprobar, cancelar, borrar scopes permanentes) requiere admin; el resto, developer. Nadie otorga un rol mayor al propio ni toca a alguien con rol superior (un admin no degrada ni saca a un owner), un token no puede ser owner y una org no puede quedar sin owner.
- **Los tokens siguen a su dueño.** El rol efectivo de un token es el menor entre su rol y la membresía actual de quien lo creó (`Authenticator.EffectiveRole`). Sacar a un miembro borra sus tokens en la org en la misma transacción; bajarle el rol acota los tokens con rol superior. El SSE re-chequea el acceso en cada ping.
- **Cerrar un comando es un solo camino.** `StoreBackend.finishCommand` cierra comando, deployment y scope en una transacción y emite después del commit. Lo usan el `result` del agente, la reconciliación del `hello` (los `acked` que no están en `in_flight` se dan por perdidos) y el reaper de `server` (cada minuto, `sent`/`acked` más viejos que `timeout_seconds` + 2 min). `approve` y `cancel` usan transiciones condicionales (`TransitionDeployment`), y `cancel` responde 409 si el agente ya hizo `ack`. Un scope en `deleting` no se pisa con estados de deploy (`SetScopeDeployStatus`).
- **rotate-token y borrar cluster cortan la conexión viva del agente** (`Hub.Disconnect`, close 1008).
- **`PATCH /v1/orgs/{org}`** (admin) para `name` y `settings` es una ruta extra respecto de `docs/api.md`: sin ella `require_approval_prod` no se podría cambiar.
- **`manifest` se guarda como texto.** La arquitectura dice jsonb, pero la API devuelve el YAML original y el CLI lo reimporta; conviene conservarlo tal cual. `manifest_sha` es SHA-256 del texto.
- **`api_tokens.role`** en vez de `scopes`: el contrato de la API asigna un rol al token.
- **El fanout de eventos es por proceso.** Con varias réplicas de la API, un cliente SSE solo ve los eventos que emite su réplica; los eventos persistidos siguen completos en `GET /events`. Para multi-réplica hace falta `LISTEN/NOTIFY` de Postgres (fuera de la Fase A).
- **`RAMPA_AGENT_IMAGE`** va al `install_command` como `--set-string image.repository=<repo> --set-string image.tag=<tag>`, las claves de `charts/rampa-agent/values.yaml` (`--set-string` para que un tag numérico siga siendo string y pase `values.schema.json`). `RAMPA_CHART_REPO` es el chart OCI y `RAMPA_PUBLIC_URL` va en `api.url`.
- **CORS** se habilita solo con `RAMPA_DEV_LOGIN=true`, para orígenes `http://localhost:*` (el dev server de Vite). En producción la SPA se sirve desde la misma API.
- **El spec es otra forma de escribir el manifest.** `POST /apps/from-spec` y `PUT /apps/{app}/spec` pasan por `manifest.FromSpec` + `MarshalManifest` y después por exactamente el mismo camino que un manifest pegado (`createApplication`, `replaceManifest`). Lo que se guarda es el YAML canónico con la cabecera "Generado por Rampa desde la web"; `GET /spec` deriva el spec del manifest guardado, sea pegado o generado. `preview` responde 200 con `valid: false` y los `details` de `FromSpec` (source inválido, scope repetido) más los de `Validate`.
- **El `scaffold.zip` lleva el `rampa.yaml` real** (`MarshalManifest` del manifest guardado, no el texto pegado) y una carpeta raíz con el nombre de la app. La org de GitHub sale de `?github_org`, después de `settings.github_org` y por último `CHANGEME`.
- **Un run de infraestructura es una fila que cambia de operación.** `destroy` y `retry` reencolan el mismo `infra_runs` (con `operation` apply o destroy) en vez de crear otro, así el estado de OpenTofu (`infra_states`, clave `run_id`) sigue siendo el mismo. El log se conserva entre intentos (`attempt` y una línea `== rampa: ... (intento N) ==` los separa). `destroying` cubre tanto "en cola para destruir" como "destruyendo"; `locked_at` distingue si algún worker lo tomó.
- **Nada sensible se persiste del run.** `inputs` no lleva el token del agente: al ejecutar, el runner **rota el token del cluster**, guarda solo el hash y pasa el texto plano por `TF_VAR_agent_token` al subproceso. El token del backend de estado también se genera por ejecución y solo se guarda su SHA-256 (`state_token_hash`). Las credenciales de la cuenta (`provider.CredentialsProvider`, AssumeRole de una hora con external ID y sesión `rampa-infra-<run>`) van únicamente al entorno del subproceso, que arranca con un entorno mínimo (PATH, HOME en el workdir, `TF_*`, `AWS_*`) y no hereda el de la API. `tofu output -json` no va al log y los outputs marcados `sensitive` se descartan.
- **Seguridad del backend de estado.** `/v1/tfstate/{run}` está fuera del grupo de sesión: autentica con el token del run (`Authorization: Bearer`, o Basic con el token como contraseña, que es lo que manda `tofu` con `TF_HTTP_USERNAME`/`TF_HTTP_PASSWORD`), busca el run por el hash y compara en tiempo constante que el id de la ruta sea el suyo: un run solo lee su estado. El estado se cifra con AES-256-GCM (`RAMPA_STATE_KEY`, 32 bytes en base64 o hex), nonce aleatorio por escritura y el id del run como dato autenticado, así un ciphertext no se puede mover de un run a otro. Si se pierde la clave, el estado es irrecuperable: hay que importar los recursos de nuevo. Locks con la semántica del backend http: `LOCK` devuelve 423 con el lock vigente si lo tiene otro ID (200 si es el mismo), `POST` exige `?ID=` del lock cuando está tomado (409 si no coincide) y `UNLOCK` con otro ID es 409.
- **Log en vivo sin inflar `events`.** Cada línea se guarda en `infra_run_logs` y se emite con `Bus.Broadcast` como `infra_run.line` (fanout en memoria, no se persiste). Las transiciones sí se persisten como `infra_run.status`. El stream `GET .../log?stream=1` se suscribe primero, manda lo guardado y deduplica por `seq`; con el estado terminal vacía lo que faltaba y cierra con `event: done`.
- **Recuperación al arrancar.** El worker marca `failed` (con `locked_at` liberado y el cluster en `failed`) los runs que quedaron tomados por un proceso anterior. Con varias réplicas de la API esto pisaría runs vivos de otra réplica; hoy el runner asume una sola réplica ejecutando infra (o `RAMPA_INFRA_CONCURRENCY` mayor en una sola).
- **`clusters.status` admite `failed`** para clusters cuyo run falló: quedan con `infra_run_id` para reintentar o borrar, y el arranque de la API no los pisa a `offline`. `POST /clusters` acepta `agent_role_arn` y el `install_command` agrega la anotación IRSA del ServiceAccount cuando lo hay.
- **Los golden paths viven en `cmd/rampa/templates`** (paquete `templates`, `embed.FS`) y los importan el CLI y la API, así el zip y `rampa init` generan lo mismo.
- **Credenciales de nubes con auth token (ADR 0004).** `GET /providers` lista los seis providers con `auth` y `terminology`. Al crear una cuenta de un provider `auth: token` sin `RAMPA_STATE_KEY` la API responde `501 not_implemented` diciendo qué falta. En `PATCH /cloud-accounts/{id}` los campos marcados `secret` en `instructions.fields` se toman de `credentials` (o de `settings`, de donde se sacan), se funden con los guardados (mandar uno lo rota, los demás se conservan), se cifran con `crypto.SealCredentials` (AAD el id de la cuenta) y van a `credentials_ciphertext`; `has_credentials` lo refleja y ninguna respuesta ni evento los devuelve. `verify` exige los campos requeridos de las instrucciones (external_ref, credenciales o settings según el caso) y descifra en memoria justo antes de `Provider.Verify`; el runner hace lo mismo antes de `CredentialsProvider.Credentials` (`Service.providerAccount`). DigitalOcean exporta `DIGITALOCEAN_TOKEN` al subproceso; su `Expires` es cero porque el token es de larga duración, y el log lo dice sin mostrarlo.
- **Bootstrap tokens.** `rampa_bootstrap_<hex>`, solo el hash en `cluster_bootstrap_tokens`, vencen a las 2 horas. Los emiten `POST /clusters/{id}/bootstrap-token` (admin), `GET /clusters/{id}/install-command` (admin; `--set-string cluster.bootstrapToken=...` en vez de `cluster.token`, sin rotar el token del cluster) y el runner al ejecutar un apply (`TF_VAR_bootstrap_token`; `aws/eks-cluster` recibe además `TF_VAR_agent_token` rotado como hasta ahora). `POST /v1/agent/bootstrap` va fuera del grupo de sesión: `ConsumeBootstrapToken` marca `used_at` en el mismo `UPDATE` que valida no usado y no vencido (dos canjes concurrentes no ganan los dos), genera **siempre** un token de cluster nuevo (el anterior deja de valer aunque no estuviera en uso), corta la conexión viva con `Hub.Disconnect` y emite `cluster.token_rotated` con `payload.via = "bootstrap"`. Los fallos se loguean con la IP y el motivo (desconocido, ya usado, vencido) y nunca con el token. Un limitador en memoria (`ratelimit.go`) acota a 10 intentos por minuto por IP y por token; el exceso responde `429` con código `rate_limited`.
- **Secretos de aplicación viajan una sola vez.** `PUT /apps/{app}/scopes/{scope}/secrets` valida los nombres con la regla de los parameters (`manifest.ValidateParameterName`), exige el scope atado a un cluster y que el agente esté online (`Hub.Online`, si no `409`), arma el `write_secret` con `target` `kubernetes` si `clusters.secret_store` es `kubernetes` o `cloud` en cualquier otro caso, persiste en `agent_commands` una copia **sin `values`** (con `keys`), guarda las claves en `scope_secret_keys` y entrega el comando con `Hub.Send`, solo por la conexión viva. `store.LiveOnlyKinds` excluye `write_secret` de la cola que el hub reenvía al reconectar: el payload guardado no está completo y reenviarlo no tendría sentido; si el agente no responde, el reaper lo cierra. Si `Send` falla entre el chequeo y el envío, el comando se cierra como `failed` y la respuesta es `409`. El evento `scope.secrets_written` lleva solo las claves; el `result` del agente se anuncia como `scope.progress` con `payload.kind = "write_secret"`. `GET .../secrets` devuelve las claves conocidas (`[]` si el scope no tiene fila). Prod exige admin.
- **`compute` del scope.** `pkg/manifest.Scope.Compute` (`kubernetes` por defecto, `serverless` reservado) sale en la respuesta de scopes y en el spec; `POST .../deployments` a un scope `serverless` responde `501 not_implemented` ("serverless llega en la ola dos"). Los efímeros heredan el `compute` de `pr` porque `ResolveScope` devuelve la plantilla.
- **El root module solo le pasa al módulo lo que el módulo declara.** `infra.RootModule` declara todas las variables conocidas de un módulo (comunes: `name`, `env`, `api_url`, `bootstrap_token`, `agent_chart_url`, `agent_image_repository`, `agent_image_tag`, `tags`) pero lee los `.tf` embebidos y solo escribe `module.<x> = var.<x>` (y `output`) para lo que el módulo declara. Así la API y `terraform/modules` pueden avanzar a ritmos distintos sin romper el apply; el tfvars también se filtra a las variables del root. `provider "aws" { region = var.region }` en AWS; `provider "digitalocean" {}` en DigitalOcean con `digitalocean/digitalocean >= 2.40` y `hashicorp/helm >= 3.0`; `tags` es `map(string)` en AWS y `list(string)` en DigitalOcean porque así lo declaran los módulos.
- **Clusters de tipo `vm`.** `clusters.kind` (`kubernetes` | `vm`) lo pone el módulo (`vm` para `aws/ec2-k3s` y `digitalocean/droplet-k3s`) o el cliente en `POST /clusters`; `secret_store` por defecto sale del módulo (`kubernetes` en DigitalOcean y OVH, el gestor de la nube en el resto). Los runs de kind `vm` crean un `Cluster` igual que los de kind `cluster` (`InfraRun.CreatesCluster`).
- **Idioma mínimo.** `users.locale` (`""`, `es`, `en`); `GET /me` devuelve `locale` (el efectivo) y `user.locale` (la preferencia); `PATCH /me {"locale"}` la guarda (solo con sesión de usuario). `auth.LocaleFromHeader` resuelve `Accept-Language` para toda request y `RequireAuth` lo pisa con la preferencia. Los mensajes todavía no están traducidos: eso es el refactor transversal del ADR 0004.

## Fuera de alcance de la Fase A (documentado, no implementado)

- Expiración automática de scopes efímeros por TTL (`ttl_expires_at` se calcula y guarda; falta el barrido).
- `logs` y `status` del agente (`protocol.KindLog` se acepta y se ignora).
- Tablas `parameters` y `services` existen en la migración pero no tienen endpoints.
- Fanout de eventos entre réplicas (también afecta al log en vivo de los runs de infraestructura: solo lo ve la réplica que ejecuta).
- Paginación en listados (salvo eventos y runs de infraestructura, con `limit`).
- Módulos de infraestructura para gcp, azure, oci y ovh: figuran en `/infra/modules` con `available: false`.
- Al rotar el token del cluster durante un apply de `aws/eks-cluster`, la conexión viva de un agente anterior (si la hubiera) no se corta; el helm upgrade reinstala el Secret y el agente reconecta con el nuevo. El canje de un bootstrap token sí la corta.
- Catálogo de mensajes localizados por código de error (ADR 0004, decisión 8): hoy solo se resuelve el idioma; los textos siguen en español.
- Serverless (`compute: serverless`, módulo `aws/lambda-scope`): ola dos; el deploy responde 501.
- Purga periódica de `cluster_bootstrap_tokens` usados o vencidos: `store.PurgeBootstrapTokens` existe pero no hay un job que la llame.
- El limitador de `POST /v1/agent/bootstrap` es por proceso: con varias réplicas el límite efectivo es el producto.
